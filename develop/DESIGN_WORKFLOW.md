# 大型设计工作流程规范

> **文档定位**：跨会话大型设计工作的标准流程，防止上下文压缩丢失工作状态。
>
> **文档结构**：5 个阶段（准备 → 设计 → 审查 → 修复 → 提交），每阶段有检查清单。
>
> **更新规范**：
> 1. 流程改进时更新对应阶段
> 2. 新增检查项追加到对应清单末尾

---

## 适用场景

- 架构重构（如引擎分离、模块拆分）
- 新子系统设计（如动画引擎、脚本系统）
- 跨多文件的大规模改造
- 预计需要多个会话才能完成的工作

---

## 阶段一：准备

### 启动检查清单

- [ ] 读取 `temp/CLAUDE_MEMORY.md` 恢复历史上下文
- [ ] 读取持久记忆目录 `~/.claude/projects/.../memory/` 中相关文件
- [ ] 读取设计文档（`develop/plans/` 下对应文件）
- [ ] 确认当前进度：哪些已完成，哪些待做
- [ ] 确认 git 状态：当前分支、未提交变更

### 进度追踪

在 `temp/CLAUDE_MEMORY.md` 末尾追加当前会话的工作状态：

```markdown
## YYYY-MM-DD 主题（进行中）

### 当前状态

一句话描述当前进度。

### 待办清单

- [ ] 任务 1
- [ ] 任务 2

### 关键架构决策（无法从代码推导）

| 方面 | 决策 |
|------|------|
| xxx  | xxx  |

### 相关文件

- 设计文档：`develop/plans/xxx.md`
```

**防臃肿规则**：

- `temp/CLAUDE_MEMORY.md` 只记两类内容：① 当前进行中的工作状态 ② 无法从代码/git 推导的架构决策
- 不记提交记录（git log）、不记文件变更清单（git diff）、不记已完成的 bug 修复（代码已记录）
- **已完成的设计工作 → 删除条目**，信息保留在设计文档 + git 历史中
- 协作约定/用户偏好只存持久记忆，不重复存 CLAUDE_MEMORY

## 阶段二：设计

### 设计文档规范

设计文档放在 `develop/plans/` 目录，文件名格式 `yyyy-MM-dd-topic.md`。

文档头部必须包含：

```markdown
# 标题

> **文档定位**：一句话说明
>
> **文档结构**：N 个设计节 + 迁移策略
>
> **更新规范**：
> 1. 设计变更需同步更新对应章节
> 2. 实现过程中发现的偏差记录在末尾「实现偏差」节
```

### 决策记录规范

每个设计决策必须包含：

| 字段 | 说明               |
|----|------------------|
| 方面 | 决策涉及的方面（如"状态管理"） |
| 决策 | 最终选择（如"单状态机"）    |
| 理由 | 为什么选这个（证据、对比分析）  |
| 备选 | 考虑过但放弃的方案        |

### 代码示例规范

设计文档中的代码示例必须：

- 使用项目编码规范（Allman 风格、4 空格缩进）
- 标注是"设计代码"还是"实现代码"
- 设计代码可能与最终实现有偏差

## 阶段三：审查

### 多轮审查流程

```
第一轮：设计完整性审查
  → 检查每个设计节是否有遗漏、矛盾、不一致
  → 输出：问题清单（P0/P1/P2/P3 级别）

第二轮：自审（逐帧推演）
  → 对每个设计点逐帧推演执行流程
  → 检查边界条件（栈空、并发、异常）
  → 输出：自审问题清单

第三轮：修复后审查
  → 验证所有修复是否正确
  → 检查修复是否引入新问题
  → 输出：最终确认
```

### 审查检查清单

- [ ] 包结构描述与详细设计是否一致
- [ ] 代码示例中的方法名/参数是否与设计一致
- [ ] 状态机的所有状态转换是否覆盖
- [ ] 帧间约束是否在所有路径上满足
- [ ] 边界条件处理（空栈、重复操作、异常）
- [ ] 文档中是否有过时的描述未更新

### 问题分级

| 级别 | 含义               | 处理方式 |
|----|------------------|------|
| P0 | 架构缺陷，会导致崩溃或数据不一致 | 必须修复 |
| P1 | 设计不合理，增加实现复杂度    | 应该修复 |
| P2 | 文档不一致或表述不清       | 修复   |
| P3 | 优化建议，不影响正确性      | 可选   |

### 进度同步

每完成一轮审查，在 `temp/CLAUDE_MEMORY.md` 中更新：

```markdown
### 审查进度

- 第一轮：X/Y 项完成
- 第二轮：X/Y 项完成
- 第三轮：待开始
```

---

## 阶段四：修复

### 修复顺序

1. **先修架构问题（P0）**：确保设计正确
2. **再修文档不一致（P1/P2）**：确保文档准确
3. **最后处理优化建议（P3）**：可选

### 修复检查清单

- [ ] 修复是否只改了声明的地方，没有遗漏其他引用
- [ ] 修复是否引入新的不一致
- [ ] 相关的记忆文件是否同步更新
- [ ] 包结构描述是否与详细设计一致

### 跨会话恢复

如果修复工作跨越多个会话：

1. 在 `temp/CLAUDE_MEMORY.md` 中记录已完成的修复和待修复的问题
2. 新会话启动时读取记忆，确认进度
3. 从上次中断的地方继续

---

## 阶段五：提交

### 提交前检查

- [ ] 所有审查问题已解决
- [ ] 设计文档内部一致（包结构 = 详细设计 = 审查结论）
- [ ] `temp/CLAUDE_MEMORY.md` 已更新最终状态
- [ ] 持久记忆文件已同步
- [ ] `develop/CHANGELOG.md` 已更新

### 提交粒度

- 设计文档单独提交（一个完整的设计阶段 = 一笔提交）
- CHANGELOG 条目与设计文档一并提交
- 不要把多个设计阶段混在一笔提交

---

## 防止上下文压缩丢失状态

### 关键原则

1. **所有状态必须落盘**：不依赖对话上下文，所有进度写入 `temp/CLAUDE_MEMORY.md`
2. **结构化记录**：用表格记录问题清单，不用自然语言描述
3. **及时更新**：每完成一个子任务就更新记忆，不要攒到最后
4. **明确断点**：会话结束时记录"下次从哪里继续"

### 记忆文件结构

`temp/CLAUDE_MEMORY.md` 中的设计工作记录应包含：

```markdown
## YYYY-MM-DD 主题（状态）

### 当前状态

一句话。

### 已完成

- [x] 任务 1
- [x] 任务 2

### 待完成

- [ ] 任务 3
- [ ] 任务 4

### 问题清单

| # | 级别 | 问题 | 状态 |
|---|------|------|------|
| 1 | P0   | xxx  | 已修复 |
| 2 | P1   | xxx  | 待修复 |

### 设计决策

| 方面 | 决策 | 理由 |
|------|------|------|
| xxx  | xxx  | xxx  |

### 相关文件

- `develop/plans/xxx.md`
```
